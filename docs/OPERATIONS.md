# Operations

Deploying, migrating, running and recovering PayRecon.

Everything here refers to code that exists. Sections marked **Not implemented**
describe a procedure whose supporting code is not built yet and say so plainly.

---

## 1. Deployment topology

Two long-lived processes plus one PostgreSQL instance.

| Process | Image               | Entry                    | Listens                 | Scaling                                                            |
| ------- | ------------------- | ------------------------ | ----------------------- | ------------------------------------------------------------------ |
| Web     | `Dockerfile.web`    | `next start` (port 3000) | HTTP 3000               | Horizontal. Stateless — sessions are in PostgreSQL, not in memory. |
| Worker  | `Dockerfile.worker` | `tsx src/main.ts`        | HTTP 3001 (health only) | Horizontal. Safe to run several; see the concurrency notes below.  |

Both images:

- use a Node 24 Alpine base with pnpm enabled via corepack,
- run as a **non-root** user (`payrecon`, uid 10001),
- set `NODE_ENV=production`,
- declare a `HEALTHCHECK`,
- contain **no secrets** — every value is injected at runtime.

`docker-compose.yml` is for **local development dependencies only** (PostgreSQL
and Mailpit). It is not a production deployment descriptor.

### Running multiple workers

This is safe by construction:

- pg-boss `singletonKey` collapses redundant jobs — one queued reconciliation per
  organization, one sync per connection, one processing job per import batch.
- `persistCandidates` takes `pg_advisory_xact_lock(hashtextextended(org))`, so two
  workers cannot race to create exceptions for the same tenant.
- Every domain write targets a unique constraint (`org+provider_id`,
  `org+external_id`, `org+fingerprint`, `org+dedupe_key`), so at-least-once
  delivery cannot produce duplicates.

`WORKER_CONCURRENCY` (default 4) sets pg-boss concurrency; the pool is sized to
`max(WORKER_CONCURRENCY * 2, 4)` connections.

## 2. Configuration

Everything is validated at startup by `packages/config/src/env.ts`. Failure
prints the **names** of the offending variables and exits non-zero. Values are
never printed.

Required in every environment: `APP_URL`, `DATABASE_URL`, `AUTH_SECRET`,
`ENCRYPTION_KEY`, `ENCRYPTION_KEY_ID`. See `.env.example` for the full annotated
list.

Production-specific rules the validator enforces:

- `APP_URL` must be `https://…` — secure cookies depend on it.
- `PLATFORM_STRIPE_SECRET_KEY` requires `PLATFORM_STRIPE_WEBHOOK_SECRET`.
- `ENCRYPTION_KEY_PREVIOUS` requires `ENCRYPTION_KEY_PREVIOUS_ID`, which must
  differ from `ENCRYPTION_KEY_ID`.

`WORKER_HEALTH_PORT` (default `3001`) is read directly by
`apps/worker/src/main.ts`. It is **not** part of the validated schema and is not
listed in `.env.example`.

## 3. Migration workflow

Migrations are checked in under `packages/db/drizzle/` and generated by
drizzle-kit. **Never hand-edit them.**

### Changing the schema

```bash
# 1. Edit packages/db/src/schema/*.ts
# 2. Generate SQL from the schema diff
pnpm db:generate

# 3. Review the generated file and its meta/ snapshot, then commit both
# 4. Apply
pnpm db:migrate
```

`drizzle.config.ts` runs with `strict: true` and `verbose: true`, so destructive
statements prompt and the generated SQL stays reviewable.

### What `pnpm db:migrate` does

`packages/db/src/migrate.ts`:

1. loads `.env` from the repository root,
2. refuses to start if `DATABASE_URL` is unset — printing the variable name, never
   the connection string, which contains a password,
3. applies pending SQL migrations from `packages/db/drizzle`,
4. **re-applies the database guards** via `applyGuards`.

Step 4 matters. The guards — the append-only audit triggers and the last-owner
trigger — are expressed as `create or replace function` plus
`drop trigger if exists` / `create trigger`, which makes them **idempotent and
safe to re-run**. Re-applying on every migration means a guard cannot be silently
lost by a schema change that recreated a table, and a fresh database always ends
up with the same protections as a long-lived one.

On failure the runner prints the error message, the PostgreSQL error code, detail
and hint — and never the connection string.

### Current migrations

| File                               | Contents                                        |
| ---------------------------------- | ----------------------------------------------- |
| `0000_parallel_captain_marvel.sql` | 36 tables and their constraints, indexes, enums |
| `0001_tidy_quasar.sql`             | `api_rate_limit_buckets`                        |

37 tables total, matching the schema.

### Rollback

There is no down-migration mechanism. Roll back by restoring from a backup (see
§7) or by writing a new forward migration. Prefer forward fixes: an additive
migration deployed before the code that needs it, and a separate later migration
that drops what is no longer referenced.

## 4. Running the worker

```bash
pnpm dev:worker                              # development, tsx watch
pnpm --filter @payrecon/worker start         # production
```

Startup order in `apps/worker/src/main.ts`:

1. Load `.env`, then `checkEnv()`. Invalid configuration prints the failing
   variable names and exits 1 — the process never starts half-configured.
2. Create the pool.
3. `getQueue()` starts pg-boss (schema `pgboss`) and idempotently creates every
   queue in `QUEUE_NAMES`.
4. `registerHandlers` attaches the handlers that exist.
5. `registerSchedules` registers the recurring jobs.
6. Start the health server.

### Registered schedules

| Queue                          | Cron                                                 | Purpose                                              |
| ------------------------------ | ---------------------------------------------------- | ---------------------------------------------------- |
| `notification.send-pending`    | `* * * * *`                                          | Drain pending deliveries (**no handler registered**) |
| `retention.cleanup`            | `0 3 * * *`                                          | Clear expired raw import content                     |
| `session.cleanup`              | `30 3 * * *`                                         | Delete long-dead sessions                            |
| `reconciliation.schedule-tick` | `RECONCILIATION_SCHEDULE_CRON` (default `0 * * * *`) | Fan out one run per organization                     |

Handlers currently registered: `reconciliation.run`,
`reconciliation.schedule-tick`, `retention.cleanup`, `session.cleanup`. The
`stripe.sync`, `import.process`, `notification.dispatch` and
`notification.send-pending` queues exist and accept jobs, but nothing consumes
them yet — **jobs sent to them will sit in the queue**.

### Graceful shutdown

`SIGTERM` and `SIGINT` stop accepting new jobs, let in-flight jobs finish
(`stopQueue({ graceful: true })`), then close the pool. Give containers a
termination grace period of at least 60 seconds so a long reconciliation is not
killed mid-run. `/health/live` reports `shutting_down` and `/health/ready`
returns 503 during shutdown, so a load balancer drains before the process exits.

## 5. Health endpoints

### Worker — implemented

| Endpoint        | Checks                                                                          | Response                                                               |
| --------------- | ------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `/health/live`  | Process is running. **Never touches the database.**                             | `200 {"status":"ok"}` or `{"status":"shutting_down"}`                  |
| `/health/ready` | `checkEnv().ok` **and** `checkDatabaseConnection(db)` **and** not shutting down | `200 {"status":"ready","checks":{…}}` / `503 {"status":"not_ready",…}` |

Port: `WORKER_HEALTH_PORT`, default 3001. Anything else returns
`404 {"error":"not_found"}`. Neither response contains configuration values —
`checks` carries booleans only.

Use `/health/live` as the container liveness probe and `/health/ready` as the
readiness probe. Probing liveness with a database check would restart a healthy
worker during a brief database blip, which is exactly the wrong response.

### Web — implemented

`apps/web/app/health/route.ts` serves `/health`. It is what
`playwright.config.ts` waits on before running the E2E suite and what
`Dockerfile.web`'s `HEALTHCHECK` probes. A second, API-scoped endpoint exists at
`/api/v1/health` (`apps/web/app/api/v1/health/route.ts`).

## 6. Retries, backoff and terminal failures

### Retry classes

Defined in `packages/jobs/src/queue.ts`:

| Class         | Attempts | Base delay | Backoff     | Used by                                |
| ------------- | -------- | ---------- | ----------- | -------------------------------------- |
| `network`     | 6        | 30 s       | exponential | `stripe.sync`                          |
| `compute`     | 3        | 60 s       | exponential | `reconciliation.run`, `import.process` |
| `delivery`    | 5        | 60 s       | exponential | notification queues                    |
| `maintenance` | 1        | 300 s      | none        | schedule tick, retention, sessions     |

pg-boss applies jitter on top of the exponential growth, which prevents a fleet
of workers retrying in lockstep after a shared outage.

`expireInSeconds` bounds runtime: 900 s for reconciliation, 1800 s for sync and
import. A job exceeding it is treated as failed and retried under its policy.

### Terminal failures

When retries are exhausted, pg-boss moves the job to its dead-letter state in the
`pgboss` schema and the job stops being delivered. There is **no operator UI for
dead-lettered jobs**. Inspect them directly:

```sql
-- Recently failed jobs
select name, state, retry_count, created_on, completed_on,
       output->>'message' as message
from pgboss.job
where state in ('failed', 'cancelled')
order by created_on desc
limit 50;

-- Failure counts by queue over the last day
select name, state, count(*)
from pgboss.job
where created_on > now() - interval '1 day'
group by name, state
order by count desc;
```

Domain-level failures are visible without touching pg-boss, because they are
recorded against the run:

- `reconciliation_runs.status = 'failed'`, with `error_category` and a sanitised,
  500-character `error_message`. `run-reconciliation.ts` records the failure and
  writes a `reconciliation.failed` audit event **before** rethrowing, so the
  failure is durable even though the job also retries.
- `sync_runs.status`, `error_category`, `error_message` for synchronisation.
- `notification_deliveries.status`, `attempts`, `last_error` for deliveries.

**Operator retry path.** Re-running is always safe: enqueue a new reconciliation
(the singleton key collapses duplicates), or re-import the same CSV (upserts
target `org+external_id`). Nothing needs to be deleted first.

### What a partial failure never does

- A failed sync page never advances a checkpoint.
  `sync_checkpoints.last_successful_at` moves only when a resource completes
  cleanly, so a failure on page 7 cannot discard the progress of pages 1–6.
- A failed reconciliation never deletes existing exceptions.
- A job queued before an organization was deleted does nothing:
  `assertLiveOrganization` returns early.

## 7. Backups

PayRecon's system of record is a single PostgreSQL database — which also holds
the pg-boss job state, so one backup covers both.

**What must be backed up:**

1. The PostgreSQL database (including the `pgboss` schema).
2. `ENCRYPTION_KEY` and `ENCRYPTION_KEY_ID` — **stored separately from the
   database**, in a secret manager. A backup without the key contains
   permanently unreadable credentials; a key stored _with_ the backup defeats the
   encryption entirely.
3. `AUTH_SECRET`. Losing it invalidates every CSRF token (users retry once) and
   makes existing `ip_hash` values incomparable. It does not invalidate sessions,
   which are opaque random tokens.

**Recommended.** Nightly `pg_dump` plus continuous WAL archiving for
point-in-time recovery. Restore-test on a schedule — an untested backup is not a
backup.

```bash
pg_dump --format=custom --no-owner --file=payrecon-$(date +%F).dump "$DATABASE_URL"
pg_restore --clean --if-exists --no-owner --dbname="$TARGET_DATABASE_URL" payrecon-2026-07-21.dump
pnpm db:migrate   # always re-apply guards after a restore
```

That last step matters: `pg_restore` may not reproduce the triggers, and the
guards are what make `audit_events` append-only. `applyGuards` is idempotent, so
running it is always safe.

## 8. Runbook — organization deletion

There are two operations because "delete my organization" and "erase every trace
of this tenant" are different requests carrying different risk.

### 8a. Soft delete — the ordinary product path

`softDeleteOrganization(db, organizationId)`.

Sets `organizations.deleted_at`. Access ends **immediately**:
`resolveOrgContext` and `listUserOrganizations` both filter deleted rows, so no
member can reach the organization on the next request, and
`assertLiveOrganization` stops queued jobs from doing further work.

Nothing is destroyed. An accidental deletion is recoverable with
`restoreOrganization`, and the audit trail survives.

**Use this for:** self-service deletion, churn, closing an account, anything
where the customer might come back or where you might need to answer a question
later.

Steps:

1. Confirm the requester is an owner (`org:delete` is owner-only).
2. Call `softDeleteOrganization`.
3. Record an audit event before the row disappears from tenant queries.
4. Tell the customer their data is retained and recoverable for your stated
   window.

### 8b. Purge — the privileged maintenance path

`purgeOrganization(db, organizationId)`.

Physically removes the tenant and everything belonging to it, **including its
audit events**.

**Why it needs special handling.** `audit_events` is append-only, enforced by a
database trigger that rejects `DELETE`. That guard is doing its job — it also
blocks the FK cascade from an organization delete. Rather than weakening the
guard (which would let any buggy or compromised code path erase history), the
purge explicitly disables `audit_events_no_delete` **inside one transaction**,
deletes the organization, and re-enables it in a `finally`. PostgreSQL DDL is
transactional, so if the delete fails the trigger is restored automatically.
`ALTER TABLE` takes an ACCESS EXCLUSIVE lock, which is acceptable for a rare
operator-initiated action and is one more reason an ordinary request cannot reach
this.

**Use this only for:** a verified erasure request (GDPR Article 17 or
equivalent), a confirmed data-subject deletion obligation, or removing test
tenants from a production database.

**Never use it as the ordinary "delete" button.**

Steps:

1. **Record the reason durably outside the tenant first** — a ticket, a legal
   record, a separate audit store. The organization's own audit rows are among
   the data about to be destroyed, so this is the only way the decision remains
   accountable.
2. Take a fresh backup, or confirm one exists that predates the purge. There is
   no undo.
3. Confirm the organization id is the intended one. Cross-check name **and**
   slug — a UUID typo is unrecoverable:

   ```sql
   select id, name, slug, deleted_at, created_at from organizations where id = '…';
   ```

4. Soft-delete first if it is not already soft-deleted, and let it sit long
   enough to catch a mistake.
5. Run the purge in a maintenance window — the ACCESS EXCLUSIVE lock briefly
   blocks all access to `audit_events`, which every write path touches.
6. Verify the trigger is back:

   ```sql
   select tgname, tgenabled from pg_trigger
   where tgrelid = 'audit_events'::regclass and not tgisinternal;
   -- tgenabled must be 'O' (enabled) for both audit_events_no_update and _no_delete
   ```

   If a crash left it disabled, `pnpm db:migrate` re-applies the guards
   idempotently.

7. Confirm removal:

   ```sql
   select count(*) from organizations where id = '…';           -- 0
   select count(*) from audit_events where organization_id = '…'; -- 0
   ```

Users are never deleted by a purge — they may belong to other organizations.
`billing_webhook_events.organization_id` is set to `NULL` rather than cascading,
so PayRecon's own billing receipts survive.

## 9. Runbook — encryption key rotation

Rotate on a schedule, and immediately if `ENCRYPTION_KEY` may have been exposed.

The design supports rotation without downtime: `decrypt` selects the key by
`key_id` (compared in constant time), so rows written under a retired key stay
readable while the new key is in use.

1. **Generate a new key and pick a new id.**

   ```bash
   openssl rand -base64 32     # the new ENCRYPTION_KEY
   ```

   Choose an id that has never been used: `k2`, `k3`, …

2. **Deploy both keys.** Move the current values down and install the new ones:

   ```dotenv
   ENCRYPTION_KEY=<new key>
   ENCRYPTION_KEY_ID=k2
   ENCRYPTION_KEY_PREVIOUS=<old key>
   ENCRYPTION_KEY_PREVIOUS_ID=k1
   ```

   Startup validation rejects a previous key without an id, an id equal to the
   active one, or a key that does not decode to 32 bytes. Restart web and worker.
   From this moment every **new** encryption uses `k2`, and every existing `k1`
   row still decrypts.

3. **Re-encrypt.** For each `stripe_credentials` row and each Slack
   `notification_destinations` row, rebuild the AAD from the row's own context
   (`buildAad({ organizationId, purpose, recordId })`), call `rotateEnvelope`, and
   write back `ciphertext`, `nonce`, `auth_tag` and `key_id` in a transaction.
   `rotateEnvelope` returns `null` when a row is already current, so the pass can
   be re-run cheaply and is safe to interrupt.

   **Not implemented:** there is no re-encryption job or CLI. The primitive
   (`rotateEnvelope`) exists; the batch driver does not.

4. **Verify no old rows remain.**

   ```sql
   select key_id, count(*) from stripe_credentials group by key_id;
   select secret_key_id, count(*) from notification_destinations
   where secret_ciphertext is not null group by secret_key_id;
   ```

5. **Retire the old key.** Only once both queries show no `k1` rows, clear
   `ENCRYPTION_KEY_PREVIOUS` and `ENCRYPTION_KEY_PREVIOUS_ID` and restart. Do not
   destroy the old key material until you have verified a restore from a backup
   taken **before** the rotation.

**If the key is lost.** Encrypted credentials are unrecoverable — that is the
point. Recovery is: disable every affected connection, notify customers, and have
them supply a new restricted key. Slack destinations must be re-added. No
operational or exception data is lost, because only credentials are encrypted.

## 10. Recovery scenarios

| Symptom                                             | Likely cause                                          | Action                                                                                                  |
| --------------------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Worker exits immediately with a list of variables   | Invalid configuration                                 | Fix the named variables. The message never prints values.                                               |
| `/health/ready` returns 503, `database:false`       | Database unreachable or pool exhausted                | Check connectivity and `max_connections`. Liveness is unaffected, so the pod is not restarted.          |
| `/health/ready` returns 503, `configuration:false`  | A variable changed to an invalid value                | Fix and restart.                                                                                        |
| Jobs enqueue but never run                          | No worker, or no handler registered for that queue    | `stripe.sync`, `import.process` and the notification queues have **no handlers yet**.                   |
| Reconciliation runs but creates nothing             | Empty window, or everything inside the grace window   | Check `diagnostics.withinPropagationGrace` and the run's `providerPayments` / `internalRecords` counts. |
| Exceptions look wrong after a data correction       | Stale exceptions from before the fix                  | Re-run reconciliation. Fixed problems are simply not re-detected; the exception stays until resolved.   |
| Duplicate exceptions for one problem                | Fingerprint inputs changed (e.g. a new `external_id`) | Investigate the fingerprint components in `RECONCILIATION_RULES.md`. Resolve the stale one.             |
| `audit_events is append-only` error on a write path | A code path attempting `UPDATE`/`DELETE`              | This is correct behaviour. Fix the caller — do not disable the trigger.                                 |
| Organization must retain at least one owner         | Last-owner guard                                      | Transfer ownership first, then remove or demote.                                                        |
| Migration fails mid-way                             | Conflicting manual change, or a failed DDL            | Migrations run in a transaction per file. Fix the cause and re-run — `applyGuards` is idempotent.       |
| Guards missing after a restore                      | `pg_restore` did not reproduce the triggers           | `pnpm db:migrate`. Verify with the `pg_trigger` query in §8b.                                           |

## 11. Routine checks

**Daily**

```sql
-- Failed reconciliation runs
select organization_id, status, error_category, created_at
from reconciliation_runs
where status = 'failed' and created_at > now() - interval '1 day';

-- Failed jobs
select name, count(*) from pgboss.job
where state = 'failed' and created_on > now() - interval '1 day'
group by name;

-- Stale sync checkpoints
select connection_id, resource, last_successful_at
from sync_checkpoints
where last_successful_at < now() - interval '6 hours';
```

**Weekly**

```sql
-- Encryption key distribution (should be a single current key id)
select key_id, count(*) from stripe_credentials group by key_id;

-- Retention cleanup is actually running
select created_at, metadata from audit_events
where action = 'retention.cleanup_ran'
order by created_at desc limit 10;

-- Audit triggers are enabled ('O' for both)
select tgname, tgenabled from pg_trigger
where tgrelid = 'audit_events'::regclass and not tgisinternal;
```

## 12. Not implemented

- **Handlers** for `stripe.sync`, `import.process`, `notification.dispatch` and
  `notification.send-pending`. Those queues exist and accept jobs, but nothing
  consumes them.
- **A dead-letter UI.** Failed jobs must be inspected with SQL against the
  `pgboss` schema.
- **A key re-encryption job or CLI.** `rotateEnvelope` exists; nothing drives it
  over the tables, so §9 step 3 is manual.
- **A metrics backend.** Structured logs and the run counters are the only
  telemetry.
- **Retention cleanup beyond raw CSV content** — expired idempotency records,
  elapsed rate-limit windows and provider-data retention are not implemented.
- **Rate limiting on authentication.** The ingestion API is rate limited; sign-in
  is not.
